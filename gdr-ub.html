灵衢总线 UB-GDR 路径技术文档

1. 项目背景

灵衢总线（UnifiedBus, UB） 是华为自研的高速互连总线，用于数据中心的服务器内、超节点间通信。

UMDK（Unified Memory Development Kit） 是以内存语义为中心的分布式通信软件库，向下驱动灵衢总线硬件，向上提供： URMA（统一远程内存访问，单边/双边/原子操作）、URPC、ULOCK、USOCK 等能力。

URMA（Unified Remote Memory Access） 是 UMDK 的核心：让应用能够像访问本地内存一样，对远端内存进行读、写、原子操作，是分布式训练/推理通信的基础。

UB-GDR 目标：让 GPU 显存成为 URMA 可寻址、可被远端 udma 引擎直接 RDMA 读写的内存段，从而在 GPU 之间、GPU 与远端节点之间实现 显存直达 的数据通路，绕开 CPU 中转与多次拷贝，把 GPU 直连的吞吐与延迟优势发挥出来。

参与仓库与分工

仓库角色关键内容
kernel/ 操作系统内核（Linux 6.6 openEuler） IOMMU/UMMU 侧 GDR 支撑：drivers/iommu/hisilicon/ummu-core/core_matt.c 新增 ummu_sva_matt_map_phys_sg 等 GDR 接口（IOMMU 支持 GDR 的补丁）；UB 总线 & UMMU 基础框架
urma_driver_netlab/ 内核态 UB 驱动族（OOT 模块，.ko） ubcore/uburma/ubagg/udma 等；其中 udma.ko + udma_nv_p2p_bridge.ko 承载 GPU P2P 内核逻辑 （nvidia_p2p_get_pages pin 显存）
UMDK_tool_netlab/ 用户态库 + 测试工具（CMake 构建） liburma.so（核心库）、liburma-udma.so（udma provider，含 is_gpu_seg ucmd）、urma_perftest（测试程序，含 CUDA/GDRCopy loader）
一句话：内核给 GDR 铺 IOMMU 路（kernel 仓库）→ udma 系列 ko 在驱动层把 GPU 显存 pin 住并建映射 （urma_driver_netlab 仓库）→ 用户态 lib + perftest 发起显存直达的读写测试（UMDK_tool_netlab 仓库）。

2. 总体流程概述

整个 ub-gdr 的激活过程，最终验证动作是：用 urma_perftest write_lat_gpu 在两台连了灵衢总线的节点上， 跑 GPU 显存之间的写延迟测试（ping-pong）。其中服务端（Server）把显存注册为一段可被远端访问的 URMA 段，客户端（Client） 通过灵衢总线的 udma 引擎把数据直接写入服务端的 GPU 显存，再收到回包，如此往返 5 万次，统计延迟。

2.1 三条测试路径

针对 GPU 内存的接入方式，perftest 支持三种 --gpu-mode，对应三种"显存/内存怎么参与 URMA 传输"的路径：

路径命令行显存参与方式当前状态
GDR-DIRECT --gpu-mode=direct cuMemAlloc 分显存 → cuMemGetHandleForAddressRange 导出 dma-buf fd，期望走 Linux 标准 dma-buf 导入通路 未打通
PEERMEM --gpu-mode=peermem cuMemAlloc 分显存 → 注册 GPU VA 段 → 内核 udma_nv_p2p_bridge.ko 调 nvidia_p2p_get_pages pin 显存页 已打通
PROXY --gpu-mode=proxy cuMemAlloc 分显存 + cuMemAllocHost 分 host 影子 buffer， 数据 显存→host 暂存→URMA 传输（"落存"中转） 已打通（兼容路径）
GDR-DIRECT 当前未打通：代码里 try_alloc_gdr() 确实通过 cuMemGetHandleForAddressRange 拿到了 dma-buf fd，但 URMA 的 ioctl ABI 中 dmabuf_fd 字段尚未正式加入（仅在头文件注释中规划），fd 最终并未传给内核。 因此 --gpu-mode=direct 实际会退化为与 PEERMEM 相同的内核通路 （is_gpu_seg=1 → nvidia_p2p_get_pages），真正的 dma-buf 直通还需后续扩展 UABI 才能落地。

2.2 端到端工作流（自然语言大粒度描述）

  1. 准备内核：编译并启动带 GDR/IOMMU 补丁的自编译内核（版本串含自定义 LOCALVERSION，如 6.6.0-gdr_xxxx_v0.1+），确认 ummu-core.ko 等基础层模块随内核加载。
  2. 构建内核态驱动：基于上述内核的 KDIR，编译 urma_driver_netlab 的 ubcore/uburma/ubagg/udma/udma_nv_p2p_bridge 等 OOT 模块；加载顺序为依赖链：先 ubcore/uburma， 最后 udma + udma_nv_p2p_bridge（bridge 在 init 时向 udma 注册 GPU P2P 回调）。
  3. 构建用户态：CMake 编译 liburma.so、liburma-udma.so、 urma_perftest，并用 isolate_umdk_gpu.sh 隔离部署（避免污染系统库）。
  4. 建链注册：两端启动 perftest，服务端分配显存/内存并注册为 URMA 段（含 GPU 标记）， 通过 TCP 控制面交换段信息（VA 等），客户端导入远端段。
  5. 跑测试：客户端/服务端按 ping-pong 协议循环执行 WRITE，记录并统计往返延迟； 根据 --gpu-mode 走 GDR-DIRECT / PEERMEM / PROXY 三条路径之一。

3. 调用链路概述

本节的视野是 二进制 / .so / .ko 级别：描述"谁调了谁、数据/控制走到哪一层"，不深入到逐行代码。 两条主链路：A 申请 & 注册流程（测试开始前的一次性建链）， B 测试循环执行期流程（5 万次热循环里每一轮都走的路径）。

A. 显存/内存申请 & 注册流程

作用：把 GPU 显存（或 host 内存）变成"两端都知道地址、内核已 pin 好页、已建好 IOMMU 映射"的 URMA 段。

本流程分为两段：A1 申请路径（分配显存/内存，拿到 VA）→ A2 注册路径（把 VA 登记到 URMA 内核、pin 页、建映射、通知对端）。

B. 测试循环执行期流程

作用：每一轮把数据从一端写入另一端显存/内存，用 flag 字节做往返同步，用 JFC 完成队列确认写入完成，测延迟。

urma_perftest: run_write_lat → run_lat_test → run_write_lat_simplex
                                          // 5 万次 ping-pong 热循环

  C1  write_lat_wait_flag()   // 轮询本端 poll flag，等对端数据/回包到达
      └─ BAR 直读(libgdrapi.so/gdrdrv.ko)  或 CUDA D2H 兜底

  C2  write_lat_store_flag() + urma_post_jfs_wr()   // 写 flag + 发 WRITE
      └─ liburma.so → ioctl → ubcore.ko → udma.ko   // DMA 写对端显存/内存

  C3  poll_jfc_until_expected_cqe()   // 等 JFC 完成队列返回 CQE，确认写入完成

  └─ 循环直到 scnt/ccnt/rcnt 都达到 iters，随后统计 min/avg/p50/p99... 延迟

关键接口：urma_post_jfs_wr()（用户态发 WR）， write_lat_wait_flag() / write_lat_store_flag()（flag 同步，GPU 场景靠 BAR 映射直读提速）， poll_jfc_until_expected_cqe()（完成轮询）。

4. Q&A

Q1：URMA Token 机制是什么？token id 和 token value 分别是什么？生命周期与用法？

URMA 的 Token 机制是"段（Segment）的访问凭证 / 访问控制"机制： 注册方（Segment 拥有者）给一段内存绑定一个 token_id + token_value， 访问方（远端 importer）必须持有匹配的凭证才能导入并访问这段内存。类比：token_id 是"钥匙的编号"，token_value 是"钥匙的齿纹"。

两个核心结构体

// 安全信息：token value —— "密码/齿纹"
typedef struct urma_token {
    uint32_t token;      // 一个 32 位值，如 perftest 硬编码 0xABCDEF
} urma_token_t;

// token id —— "钥匙容器"，持有者信息 + 引用计数
typedef struct urma_token_id {
    urma_context_t  *urma_ctx;   // 归属的 URMA 上下文
    uint32_t         token_id;   // 分配的 token 编号
    uint64_t         handle;     // 内核对象句柄
    urma_ref_t       ref;        // 引用计数（生命周期管理）
    urma_token_id_flag_t flag;   // multi_seg 等标志
} urma_token_id_t;

相关控制位：token_policy（0=NONE / 1=PLAIN_TEXT / 2=SIGNED / 3=ALL_ENCRYPTED，决定校验严格度）、 token_id_valid（0=不校验 token_id / 1=必须匹配）。

生命周期（perftest 视角）

  1. 分配：服务端 urma_alloc_token_id(ctx) → 得到 urma_token_id_t（token_id + handle）。
  2. 绑定：服务端 urma_register_seg() 时在 urma_seg_cfg_t 里带上 token_id 指针和 token_value（perftest 固定 g_perftest_token = {0xABCDEF}）。
  3. 交换：服务端经 TCP exchange_seg_info 把 urma_seg_t（内含 token_id）发给客户端。
  4. 导入：客户端 urma_import_seg(ctx, &remote_seg, &g_perftest_token, ...)， 用相同的 token_value 作为凭证去导入远端段；内核校验 token 匹配后才允许访问。
  5. 释放：段注销后 urma_free_token_id() 释放 token_id（引用计数归零）。
一句话：token_id = 段访问凭证的"编号/身份"（谁发的、发给哪段），token_value = 访问的"口令" （两端一致才放行）。perftest 里两端用同一个硬编码 0xABCDEF，属于最小化测试用法； 生产环境可配合 token_policy 升级为签名/加密校验。
Q2：出现了很多 ctx，比如 perftest_context_t、urma_context_t 等，它们都是什么？各自保存了哪些信息？

代码里 ctx 满天飞，但其实是不同层级的"上下文"，各自管好自己的那一层资源。按"上 → 下"排序：

1. perftest_config_t —— "测试配置"（要做什么）

命令行参数解析的静态结果：测试类型（cmd）、设备名（dev_name）、消息大小 （size）、迭代次数（iters）、GPU 模式（gpu_mode）、server_ip、jetty 数等。 它描述"这场测试想怎么跑"，不持有运行时资源。

2. urma_context_t —— "URMA 设备连接句柄"（最底层，直接对着硬件）

typedef struct urma_context {
    struct urma_device *dev;     // 对应的 URMA 设备对象
    struct urma_ops *ops;        // 设备操作表（open/close/ioctl...）
    int dev_fd;                  // 设备 sysfs 文件 fd（ioctl 入口）
    int async_fd;                // 异步事件文件 fd
    urma_eid_t eid;              // 本端在 UB 网络里的端点 ID（寻址用）
    uint32_t eid_index;
    uint32_t uasid;              // 当前进程的 uasid
    ...
} urma_context_t;

它是进程与一块 URMA 设备之间的"打开的连接"，所有设备级操作（建 jetty、注册段、发 WR）都挂在它上面。

3. perftest_context_t —— "测试运行时上下文"（最顶层，包揽一场测试的全部资源）

typedef struct perftest_context {
    urma_eid_t  eid;              // 本端 EID
    urma_context_t *urma_ctx;     // ← 内嵌 URMA 设备连接
    urma_token_id_t **token_id;   // 分配的 token（Q1）

    // jetty / 队列资源
    urma_jfs_t **jfs;  urma_jfr_t **jfr;      // 发送/接收工作队列
    urma_jfc_t **jfc_s; urma_jfc_t **jfc_r;   // 完成队列
    urma_jetty_t **jetty;                     // 双工 jetty
    uint32_t jetty_num;

    // 内存/buffer 资源
    void **local_buf;  uint64_t buf_size;  uint64_t buf_len;  // 收发 buffer
    urma_target_seg_t **local_tseg;                          // 本地段
    perftest_gpu_buffer_t *gpu_bufs;  uint32_t gpu_bufs_n;   // GPU buffer 描述符

    // 远端信息 + 导入
    urma_seg_t *remote_seg;          // 对端段（TCP 交换来的）
    urma_target_seg_t **import_tseg; // 导入的远端段

    run_test_ctx_t run_ctx;          // 运行期：WR 链、时间戳数组、计数器
    ...
} perftest_context_t;

它是"跑完一场测试所需全部东西的容器"：一端连接（urma_ctx）、一堆队列、收发 buffer、 本地/远端段、GPU 描述符、运行期统计上下文。整个 main 流程在 create_ctx 里把它填满，run 阶段读它，destroy_ctx 里倒序释放。

关系一句话总结

perftest_config_t 定"策略"（想怎么测）→ urma_context_t 管"连接"（对一块 URMA 硬件的句柄）→ perftest_context_t 管"资源"（一场测试的全部运行时状态，内嵌 urma_ctx）。 三者的关系：perftest_context 包含 urma_context；两者都由 perftest_config 驱动的流程创建。
